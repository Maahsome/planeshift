# Implementation Plan: add context

- [x] **🎟️add context**
  - **Description:** Implement Jira ticket PSFT-15 by adding a top-level `planeshift context` command with `set` and `get` subcommands. Persist the workspace slug and project identity under the existing Viper-managed YAML configuration as `context.workspace`, `context.project.id`, and `context.project.name`. Support changed-only non-interactive updates through `--workspace` and `--project`, and use `github.com/AlecAivazis/survey/v2` for the no-flag flow: prompt for the workspace, list projects through the existing Plane Projects client, let the user select by project name, and persist the selected name and ID. Make `context get` use the existing JSON, YAML, GRON, text/table, and raw output dispatch without exposing unrelated configuration or credentials.
  - **Scope:**
    - **In scope:** A typed context model in `@config/context.go` and `@config/config.go`; centralized context resolution and persistence in `@cmd/root.go`; a new `@cmd/context` Cobra package with separate parent, `set`, `get`, and helper/test files; registration and command-name constants in `@cmd/root.go` and `@config/aliases.go`; safe context help in `@help/context_help.go`, `@help/help.go`, and `@help/root_help.go`; the explicitly requested `survey/v2` dependency in `@go.mod`/`@go.sum`; focused root/config/command tests; and black-box help coverage in `@functional/functional_test.go`.
    - **Out of scope:** New Plane endpoints, a new HTTP transport, a second Viper/configuration path, context environment variables, a context reset/delete command, project/workspace resource changes, generated SDK code, unrelated output-format changes, live interactive/API tests, credential-bearing examples, or changes to existing Project, State, Work Item, and Version behavior. Do not modify `@spec/plane-api.yaml`; the interactive flow reuses the already implemented Projects list contract.
