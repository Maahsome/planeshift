#### Prompt

You are an AI coding agent working in the `planeshift` repository. Read `AGENTS.md`, `CONSTITUTION.md`, `ARCHITECTURE.md`, and `LOCAL_BUILD.md` before editing.

Build the smallest reusable foundation needed for every resource prompt in this directory. Do not implement resource-specific Plane endpoints in this work item.

##### Governing architectural decision protocol

Before changing package boundaries, command grammar, configuration shape, or transport behavior, explicitly cite the applicable Constitution sections:

- **Owned Domains**: the repository owns CLI registration/execution, local configuration/environment resolution, output formatting, logging, and help text.
- **Forbidden Dependencies & Protected Zones**: do not add third-party dependencies or commit generated/OpenAPI client code without explicit team approval.
- **Security & Resilience Hardlines**: protect credentials and continue using `createRestrictedConfigFile` with mode `0600` for auto-created configuration.
- **Architectural & Async Invariants**: register commands below `cmd.RootCmd`, keep configuration access centralized in `cmd/root.go`, preserve package dependency direction, and do not introduce asynchronous processing.
- **Coding Conventions**: respect the existing `cmd`, `config`, `objects`, `common`, and `help` responsibilities and `config.Outputtable` output dispatch.

The repository currently records no HTTP-client architecture or API command grammar. That specific choice is an uncharted area: state the proposed minimal decision and its consequences in the implementation notes, and request/team-review an ADR update if the choice changes a protected boundary. Keep the design easy to replace.

##### Plane contract

Use the official [Plane API introduction](https://developers.plane.so/api-reference/introduction.md) as the cross-cutting contract:

- Plane Cloud uses `https://api.plane.so/api/v1/`; self-hosted installations use the configured host with `/api/v1/`. Avoid double-prefixing when users provide a base URL.
- Support exactly one configured credential mode per request: `X-API-Key` or `Authorization: Bearer ...`. Never print credentials or sensitive upload data.
- Use JSON for normal request/response bodies, standard REST verbs, context cancellation, bounded timeouts, and the documented 200/201/204 handling. Never attempt to decode a 204 body.
- Implement cursor pagination with `per_page` (server maximum 100), `cursor`, all documented response metadata, and optional `fields`/`expand` query values without losing unknown query parameters needed by resource slices.
- Preserve response headers relevant to rate limiting (`X-RateLimit-Remaining` and `X-RateLimit-Reset`) in a safe structured form. Do not add unbounded automatic retries; if retry behavior is proposed, record it as a separate reviewed decision.
- Use current `/work-items/` routes when endpoint pages document them. Do not add deprecated `/issues/` aliases. Some documentation directory names still contain `issue` or `issue-types`; never infer a server path from a documentation slug.
- Support streaming/multipart or presigned-storage upload requests as a distinct path from authenticated JSON API calls. Honor returned method, URL, headers, and form fields exactly.

##### Implementation scope

1. Define the minimal client/configuration interfaces and place them according to the repository’s existing package conventions. Centralize Viper/environment resolution in `cmd/root.go`; make base URL, credential mode, timeout, and output settings testable.
2. Implement a standard-library HTTP transport using `net/http` and `encoding/json` unless the reviewed architectural decision requires otherwise. Build URLs safely, encode query values correctly, set `Accept`/content headers appropriately, and attach only the selected auth header.
3. Add typed shared representations for API errors, pagination metadata, rate-limit metadata, and raw/dynamic JSON fields. Make errors retain status code and a bounded safe response message while avoiding secret leakage.
4. Define the resource-client and CLI registration seam that all 49 resource prompts can reuse. Resource slices must not duplicate request construction, auth, pagination, output conversion, or error handling.
5. Add test helpers around `httptest.Server` for asserting method/path/query/header/body and returning JSON, empty, malformed, and non-JSON responses. Include tests for both credential modes, invalid configuration, URL joining, cancellation/timeout, pagination, rate-limit headers, and 204 handling.
6. Add only the minimal command/help/config wiring required to exercise the foundation and make the resource prompts straightforward. Do not add speculative endpoints or broad abstractions.

##### Definition of done

- The foundation contract is documented in code comments or repository documentation, including the uncharted-area decision note.
- No new third-party dependency or generated SDK is introduced.
- Credential handling, restricted config-file permissions, command registration, output dispatch, error/status handling, pagination, uploads, and safe logging are covered by deterministic tests.
- Existing version commands retain their behavior.
- `gofmt` is clean and `CI=true go test -count=1 ./...` passes.
- The documented build workflow in `LOCAL_BUILD.md` remains valid.
